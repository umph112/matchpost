## 1. 딜시트 진행바 — 방문은 조건부

**단계는 하나의 목록이고 방문만 끼어든다. 별도 흐름이 아니다.**
```
협의 → 확정 → 가이드 → [방문] → 원고 → 수정/컨펌 → 게재 → 정산
                        ↑ campaign.type === '지역' 일 때만
```
| 구분 | 방문 | 단계 |
| --- | --- | --- |
| 지역 | ○ | 8 |
| 제품 | ✕ | 7 |
| 기자단 | ✕ | 7 |

제품과 기자단은 **딜시트상 동일**하다. 보내는 것이 제품이냐 자료냐의 차이일 뿐이다.
구현: `campaign.type === '지역' ? STAGES : STAGES.filter(s => s !== '방문')`
⚠️ 프로토타입에 있는 「캠페인 구분」 토글은 **두 경우를 보여주기 위한 것**이다. 실제로는 만들지 않는다.

**기한 칩** — 진행바 아래, 현재 단계 라벨 옆
- 기한이 붙는 체크포인트는 **4개뿐**: 가이드 · 원고 · 게재 · 정산
- ⚠️ **방문에는 기한이 없다.** 협의로 정한 날이지 마감이 아니다. 날짜만 표시, D-day·지연 없음
- 표기: `8/13 · D-11` / 귀책 상계로 밀렸으면 `8/11 → 8/13 · D-11` (원래 날짜 함께)
- 색: 지연 `#FEE2E2/#DC2626` · D-3 이내 `#FEF3C7/#B45309` · 그 외 `#F1F1F4/#7C7C88`

⚠️ **기한·D-day는 하나의 원본에서만 파생시킨다.** 상단 「공통 일정」 스트립과 행별 칩이
다른 날짜를 쓰면 안 된다 (프로토타입에서 실제로 났던 버그).

## 2. 정산 확인 모달 (광고주)

「정산 완료로 기록」 클릭 → 확인 모달. 폭 520.

- 부제: `아래 N명에게 결제를 모두 마치셨나요? 송금은 광고주가 직접 하고, 이 화면은 그 기록을 남깁니다.`
  ⚠️ 「지급하기」가 아니라 **「기록」**이다. 매치포스트는 송금을 대행하지 않는다
- **세무자료 미수령자는 자동 제외** — `대상 5명 (세무자료 미수령 3명 제외)`
- **3.3% 원천징수 토글** — 켜면 실지급액 즉시 재계산.
  설명: `개인 인플루언서 정산을 위한 소득세 원천징수 신고에 필요한 자료를 전달받으세요.`
- 금액 3줄: 지급 총액(세전) / 원천징수액 / **실지급액**(크게)
- **「기록하면 이렇게 됩니다」 4줄** — `settleCampaign` 이 실제로 하는 일 그대로:
  정산 기록(수정 불가) · 양쪽 3,000C · 상호 평가 요청 · 5일 뒤 연락처 차단
- 되돌릴 수 없으므로 무엇이 바뀌는지 **누르기 전에** 보여준다

⚠️ 모달 카드에 `onClick={e => e.stopPropagation()}`. 오버레이만 닫기 (프로토타입에서 났던 버그)

## 3. 입금 확인 (인플루언서) ⭐ 신규 — 서버 포함

### 왜 필요한가
매치포스트는 송금을 대행하지 않는다. **광고주가 실제로 결제하지 않고 완료 처리할 수 있다.**
이 확인이 유일한 안전장치다.

### 두 경우를 섞지 않는다
| 상황 | 처리 |
| --- | --- |
| 결제일 지남 · **광고주가 아직 안 누름** | **자동 미수금 분류** + 양쪽 알림. 인플루언서에게 묻지 않는다 |
| 광고주가 **결제 완료를 누름** | 그때 인플루언서에게 **입금 확인** 요청 |

**자동 미수금** — 결제 예정일 다음 날 배치가 전환. 알림 D+1 · D+3 · D+7.
광고주 정산 성실도에 지연 집계. 광고주가 뒤늦게 누르면 입금 확인 흐름으로 넘어간다.

### 입금 확인 모달 (폭 480)
- 뜨는 조건 **두 개 모두**: ① 확정된 결제 예정일 도래 ② 광고주가 결제 완료 기록
- 헤더: `{브랜드}가 정산을 완료했다고 기록했어요`
- 두 날짜 병기: `결제 예정일 7/31 · 광고주 기록 8/1`
- **`기록과 입금은 다릅니다`** 문구 필수 — 이 화면의 존재 이유다
- 금액: 계약 금액(세전) / 3.3% 원천징수 / **들어왔어야 할 금액**(세후, 크게) + 입금 계좌

⚠️ **버튼 위계가 뒤집혀 있다. 의도한 것이다.**
| 버튼 | 스타일 | 동작 |
| --- | --- | --- |
| **「입금된 게 없어요 — 브랜드에 알리기」** | 주 버튼 · 빨강 | 신고 |
| 「잘 받았어요 · 닫기」 | 보조 · 아웃라인 | 정상 처리 |

안내문: `들어왔으면 따로 하실 일이 없습니다 — 그대로 닫으면 정상 처리돼요.`
→ 정상 입금은 **아무 액션도 요구하지 않는다.** 매번 확인을 강요하면 대충 누르게 되고
   그러면 신고 자체가 무의미해진다. **부정 신고만 액션으로 둔다.**

### 매출 반영 — 숫자가 움직여야 한다
⚠️ **확인 전에는 매출 확정분에 넣지 않는다.**
- 인플루언서 매출 카드에 `입금 확인 대기 300,000` 앰버 줄을 따로 표시
- 확인을 누르면 그때 8월 매출에 더해진다 (300,000 → 600,000)
- 홈 KPI도 **같은 원본에서 파생**시킨다. 하드코딩하면 어긋난다 (실제로 났던 버그)

### 서버
```sql
alter table proposals
  add column if not exists paid_confirmed_at timestamptz,   -- 인플루언서 입금 확인
  add column if not exists paid_disputed_at  timestamptz;   -- 미입금 신고
```

## 4. 재정산 루프 ⭐ 신규 — 서버 포함

```
인플루언서 「입금된 게 없어요」
  → 해당 딜 = 미수금 · 캠페인 = 종료 불가(재정산 대기)
  → 광고주 알림 + 정산 화면에 「재정산 필요」로 복귀
  → 광고주가 실제 결제 후 다시 「정산 완료로 기록」
  → 신고한 인플루언서에게만 입금 확인 재요청
  → 신고 없이 넘어가야 비로소 완료
```

```sql
create table if not exists settlement_attempts (
  id uuid primary key default gen_random_uuid(),
  proposal_id uuid not null references proposals(id) on delete cascade,
  attempt_no  int  not null,
  recorded_at timestamptz not null default now(),
  disputed_at timestamptz,
  resolved_at timestamptz
);
```

- ⚠️ **`settled_at` 을 지우지 않는다.** 회차를 따로 쌓는다
- **여러 명이면 신고한 사람만** 다시 확인 요청을 받는다. 정상 처리된 사람은 다시 묻지 않는다
- 캠페인은 **한 명이라도 미해결 신고가 있으면 종료 불가**
- `deal_complete` 크레딧은 **첫 기록 시 1회만** — `ref_id + reason_code` 중복 차단(celebrate와 동일)
- **재정산 2회 초과 시 운영팀 자동 에스컬레이션**
- 정산 성실도는 최초 기록일이 아니라 **신고 없이 확정된 날**로 집계
  → 허위 기록으로 지표를 관리하는 것을 막는다

## 5. 상호 평가 모달 (양쪽 공통, 폭 460)

정산 완료 → 알림/임박 카드 → 모달. **1화면 30초.**

구성: 별점 5 → 태그(복수) → **운영팀에만 보이는 비공개 코멘트** → 제출
- 별점 없으면 제출 비활성. 그 외 강제 입력 없음
- 태그 — 광고주를 평가: `결제가 정확해요` `가이드가 명확해요` `요구가 합리적이에요` `소통이 빨라요` `다시 함께하고 싶어요`
  / 인플루언서를 평가: `일정을 잘 지켜요` `소통이 빨라요` `콘텐츠 퀄리티가 좋아요` `다시 함께하고 싶어요`
- 제출 버튼: `평가 보내고 1,000C 받기`
- 하단 고정: `내가 남긴 평가는 상대에게 공개되지 않습니다. 여러 건이 모이면 평균만 프로필에 표시돼요. 제출 후에는 수정할 수 없습니다.`

⚠️ **개별 평가를 반환하는 API 를 만들지 않는다.** RLS로 `rater_id = auth.uid()` 만 조회 가능.
공개는 집계뿐 — 별점 **5건 이상**, 태그는 **3명 이상**이 고른 것만.

## 10. 블로그 평가 산식 수정 ⭐ (`scripts/blog_analyzer.py`)

제목 전체 검색을 배점에서 뺀 것은 정확한 판단이다. 세부 등급(B-3)도 좋다.
문제는 **배점 100점 중 실제로는 35점 한 축만 작동한다**는 것이다.

merry9849 실측 대입:
| 항목 | 배점 | 실제 | 이유 |
| --- | --- | --- | --- |
| 일 방문자 162 | 40 | **0** | 새벽 수집이라 그날 방문자가 안 쌓임 |
| 포스팅 빈도 `null` | 15 | **0** | 파싱 실패 = 감점 |
| 이웃 325 | 10 | **0** | 컷(3,000)이 너무 높음 |
| 노출 | 35 | 35 | — |

→ 35점 전부가 노출에서 나왔고 **나머지 65점이 통째로 죽었다.**

### ① `visitor_today` — 수집 시각을 22시로 고정하고 그 값을 쓴다 (최우선)
40점짜리 최고 배점이 **"몇 시에 크롤링했나"** 로 결정되고 있었다(새벽 수집 → 162).

**크롤링 시각 = 매일 22:00 (KST)** 로 고정한다.
네이버 등 플랫폼은 **0시에 방문자 카운터가 리셋**되므로, 22시면 그날 트래픽이
사실상 다 쌓인 시점이다. 인플루언서가 늘어 수집이 오래 걸려도 자정 전에 끝난다.

```
cron: 0 22 * * *  (Asia/Seoul)
```
- ⚠️ **배치가 자정을 넘기면 그날 값이 아니라 다음 날 초기값을 긁는다.**
  수집 시작 시각을 기록하고, `crawled_on` 은 **배치 시작일 기준**으로 고정한다
  (00:30에 처리된 유저도 전날 날짜로 저장)
- ⚠️ 유저가 늘어 2시간 안에 못 끝나면 **21시로 앞당기지 말고 배치를 분산**한다
  (요일별 그룹). 시각이 흔들리면 유저 간 비교가 깨진다
- `visitor_total` 도 매일 저장해 **전일 대비 차분**을 함께 남긴다.
  22시 값과 차분이 크게 어긋나면 수집 실패를 의심할 수 있는 검증 수단이 된다
- 첫날처럼 비교 대상이 없으면 **이 항목을 빼고 환산**한다 (아래 ④)

### ② `post_frequency` — null 과 0 을 구분
`PostTitleListAsync` 가 10개만 주고 날짜 파싱이 실패하면 `null` 이 된다.
지금은 **수집 실패가 곧 감점**이라 31개 발행한 블로그가 빈도 0점을 받는다.
- `null` 이면 0점이 아니라 **항목 자체를 제외**하고 나머지로 환산
- 파싱 실패율을 줄이려면 `countPerPage` 를 30으로 올려 표본을 넓힌다

### ③ 이웃 수 컷 하향
3,000명부터 점수가 붙는데 실제 협업 가능한 블로거 상당수가 그 아래다.
```
100,000+ → 10 / 30,000+ → 8 / 10,000+ → 6 / 3,000+ → 4 / 1,000+ → 2 / 300+ → 1
```

### ④ 결측 항목은 제외하고 환산
```python
score = sum(획득점수) / sum(측정가능한_항목의_만점) * 100
```
수집 실패를 실력 부족으로 읽지 않게 한다. **측정 불가 항목 수도 함께 저장**해
2개 이상 결측이면 화면에서 `측정 중` 으로 표시하고 등급을 내지 않는다.

### ⑤ 이력 보존 (지금 안 하면 과거가 사라진다)
`upsert(on_conflict='user_id')` 라 매번 덮어쓴다 → 등급 추이·성장 그래프를 만들 수 없다.
```sql
create table if not exists blog_analytics_history (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  crawled_on date not null,
  blog_grade text, grade_score int,
  visitor_total bigint, visitor_daily int,   -- 차분으로 구한 실제 일 방문자
  neighbor_count int, post_count int, post_frequency numeric,
  exposure_rate numeric, avg_rank numeric,
  missing_metrics int,
  unique (user_id, crawled_on)
);
```
`blog_analytics` 는 최신 스냅샷 유지, 히스토리는 여기에 append.

### ⑥ 추적 대상 = **그날 발행한 포스팅만, 최대 5개**
지금은 최근 7개를 매번 다시 검사한다 → 같은 글을 며칠씩 중복 조회하면서 호출만 낭비한다.

```python
today_posts = [p for p in posts if _parse_naver_date(p['addDate']) == batch_date][:5]
```
- **그날 올린 글만** 검사하고 이전 글은 무시한다
- 발행이 없는 날은 노출 검사를 건너뛴다 (API 0회)
- 하루 5개 초과 발행 시 **최신 5개만**

이렇게 매일 쌓으면 **포스팅 단위 노출 이력**이 자연히 축적된다 — 지금의 스냅샷 방식보다
훨씬 값어치 있는 데이터가 된다. 발행 시점의 노출 성적을 글마다 남기는 것이기 때문이다.

```sql
create table if not exists blog_post_rankings (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  log_no      text not null,
  published_on date not null,
  checked_on   date not null,          -- 배치 시작일
  title text,
  keywords jsonb,                       -- [{keyword, found, rank}, ...]
  exposure_rate numeric,                -- 이 글의 키워드 노출률
  avg_rank numeric,
  unique (user_id, log_no, checked_on)
);
```
- 등급 계산의 노출 점수는 **최근 30일 누적 `blog_post_rankings`** 에서 뽑는다.
  하루치만 보면 발행이 없는 날 0점이 되어 등급이 요동친다
- 발행 직후 순위는 계속 변하므로, 여력이 되면 **D+7 에 한 번 더** 재검사해
  `checked_on` 을 다르게 남긴다 (초기 노출 vs 정착 노출을 구분할 수 있다)

**API 호출량** — 인당 **하루 최대 20회**(5글 × 4) + 카테고리 3회.
발행 없는 날은 0회. 네이버 일 25,000회 기준 **약 1,000명 이상** 수용 가능해진다.
초과하면 카테고리 체크를 주 1회로 돌리고 유저를 요일별로 분산한다.

### ⑦ 자잘한 것
- `datetime.utcnow()` deprecated → `datetime.now(timezone.utc)`
- 등급 산식과 컷을 **인플루언서에게 공개**한다 (「내 채널」 화면).
  기준을 알아야 올릴 수 있고, 공개된 기준은 분쟁 시 근거가 된다

### ⑧ 화면에서 「제목 전체 검색 순위」를 숫자로 보여주지 않는다
산식에서는 뺐는데 **화면에는 아직 1위·2위로 남아 있었다.**
내 글 제목을 통째로 검색하면 당연히 내 글이 1위다 — 실력이 아니라 색인 여부일 뿐인데
광고주가 「1위」를 보면 대단한 성과로 오해한다.

| 위치 | 바꿀 표시 |
| --- | --- |
| 제목 전체 검색 결과 | 순위 대신 **`검색 반영` / `미반영`** 배지 |
| 숫자 자리 | **키워드 최고 순위** — `최고 6위` (실제 사람이 검색하는 2-gram 기준) |
| 보조 | `2/3 노출` — 그 글의 키워드 중 몇 개가 잡혔는지 |
| 하나도 안 잡히면 | `노출 없음` (회색). `—` 로 두지 않는다 |

이렇게 해야 **화면과 산식이 같은 것을 말한다.** (프로토타입 반영 완료)

### ⑨ 「이 블로그의 특징」 자동 요약 — 등급 보정 대신 맥락 제공
등급 산식은 **4개 지표 그대로**(일 방문자·이웃 수·발행 빈도·키워드 노출도).
신생 블로그 보정은 **하지 않는다.**

대신 최근 30일 글에서 요약 한 단락 + 태그 4종을 자동 생성한다.

| 항목 | 뽑는 방법 |
| --- | --- |
| 주제 | 포스팅 제목의 2-gram 중 빈도 상위 명사군 → 분야 상수에 매핑 |
| 지역 | 제목에서 행정구역명 추출 후 상위 2–3개 (`수도권·강원`) |
| 형식 | 제목 어미 패턴 (`후기`/`총정리`/`추천`) → 방문 후기형 / 정보 정리형 / 추천형 |
| 발행 주기 | `post_frequency` → `주 2–3회 발행` |

- 광고주 **검색 결과 카드와 프로필**에 함께 노출한다 (등급 옆)
- **본인이 고칠 수 있어야 한다** — `profiles.blog_summary`, 비면 자동 생성값 사용
- 요약은 사실 서술만. 「최고의」 같은 평가어 금지

⚠️ 이게 지역 블로거 문제의 해법이다. 큰 키워드 순위만 보면 지역 블로그는 늘 불리한데,
등급을 손대면 기준이 흐려진다. **숫자를 그대로 두고 맥락을 덧붙인다.**

### ⑪ 포스팅 노출 점수를 「예상 유입량」으로 — 롱테일 만점 문제 해결

현재 산식은 **순위만** 본다. 경쟁이 없는 롱테일 키워드에서 5위를 해도 만점이 나온다.
merry9849 가 노출 35/35 만점인데 누적 방문자가 8,892명뿐인 이유가 이것이다.

**바꿀 것 — 순위 대신 예상 유입량**

```
키워드별 예상 유입 = 월간 검색량 × 순위별 CTR
포스팅 노출 점수  = 최근 30일 발행 글의 예상 유입 합계를 구간 점수화
```

| 순위 | CTR |
| --- | --- |
| 1 | 20% |
| 2–3 | 10% |
| 4–5 | 6% |
| 6–10 | 3% |
| 11–20 | 1% |
| 21–30 | 0.4% |
| 31+ | 0.1% |

- 월간 검색량은 **네이버 검색광고 API**(`/keywordstool`)에서 받는다. PC+모바일 합산
- 검색량은 `keyword_search_volume` 테이블에 캐시하고 **월 1회만** 갱신 — 자주 안 바뀐다
- API 연동 전 임시 대응: 노출 점수에 상한을 걸고 일 방문자와 교차 검증
  (노출 점수는 높은데 방문자가 적으면 롱테일이므로 상한 적용)

**화면 표기** — 「검색으로 들어오는 사람 · 월 180명」을 요약 스트립에 추가.
순위 숫자보다 이 값이 위에 와야 한다. 광고주가 사는 것은 순위가 아니라 유입이다.

⚠️ 이 변경으로 merry9849 는 노출 35 → **12점**, 총점 35 → **12점(D-3)** 이 된다.
낮아지는 게 맞다. 지금 값이 틀린 것이었다.

### ⑰ 캠페인 등록 — 담당자 연락처 필드

「예산 · 결제」 레일 최하단에 `담당자 연락처` 블록을 추가한다.

| 필드 | 필수 | 비고 |
| --- | --- | --- |
| `manager_phone` | **필수** | 담당자 휴대폰. 등록 검증에서 막는다 |
| `company_phone` | 선택 | 회사 대표번호 |

**저장 위치는 두 곳 — 계정이 기본값, 캠페인이 덮어쓰기.**

```
profiles.manager_phone / company_phone   -- 가입 시 입력 (휴대폰 필수)
campaigns.manager_phone / company_phone  -- 비면 계정 값을 쓴다
```

- **가입 폼**에서 담당자 휴대폰을 필수로 받는다
- **캠페인 등록 폼**은 계정 값을 불러와 채운다 — 「가입 정보에서 불러왔어요」
- 「**이 캠페인만 다르게**」를 누르면 그 캠페인에만 다른 번호를 넣는다.
  계정 기본값은 건드리지 않는다 (캠페인별 담당자가 다른 회사가 있다)
- 인플루언서에게 보여줄 때: `campaigns.manager_phone ?? profiles.manager_phone`
- 라벨 아래 한 줄 — 「양쪽 확정 뒤에만 인플루언서에게 보여요」
- 앰버 안내 — 「미수금이 생기면 인플루언서에게 **휴대폰 번호가 먼저** 안내됩니다」
- 기존 캠페인은 휴대폰이 비어 있으므로, **다음 수정 시 입력을 요구**한다(소급 강제는 하지 않음)

⚠️ 등록 시점에 알려야 한다. 미수 상황에서 뒤늦게 요구하면 이미 늦다.

### ⑯ 미수금 카드 — 전화번호 직접 노출

「놓치면 안 되는 일」의 미수금 카드 CTA 를 `거래처에 연락 →` 에서 **번호 자체**로 바꾼다.

```html
<a href="tel:01044723318">📞 010-4472-3318</a>
```

**노출 우선순위 — 담당자 휴대폰 › 회사 대표번호.**
대표번호는 담당자에게 닿지 않는다. 미수 상황에서 교환원을 거치면 그 자리에서 포기하게 된다.

- **PC** — 번호가 그대로 보인다. 옮겨 적을 필요 없이 바로 건다
- **모바일** — 같은 마크업이 탭 즉시 통화로 이어진다
- 번호는 `proposals` 확정 시 공개된 광고주 연락처. **미수 상태에서는 차단 예약이 걸리지 않는다**
  (정산 미완료 건은 연락 경로가 계속 열려 있어야 한다 — 기존 결정)
- 번호가 없으면 「대시로 문의 →」로 대체

⚠️ 돈을 못 받은 상황에서 단계를 하나라도 더 거치게 하면 안 된다.

### ⑮ 다른 채널 — 등록은 받고 분석은 「준비 중」

**분석은 블로그만.** 유튜브·인스타그램·틱톡은 등록만 받는다.

- 「내 채널」 좌측 하단에 `등록한 다른 채널` 카드 — 채널명 + 계정 + `분석 준비 중` 회색 칩
- 등록한 채널은 **광고주 검색·프로필에 그대로 노출**한다. 수치만 없을 뿐 채널 보유는 사실이다
- 광고주 검색의 채널 필터도 그대로 동작한다 (등급 정렬만 블로그 기준)
- 안내 문구 — 「채널마다 봐야 할 지표가 달라 순서대로 붙이고 있습니다」

**지표를 채널 간에 돌려쓰지 말 것.** 블로그는 검색 유입이 핵심이지만
유튜브는 조회수·시청 지속률, 인스타는 저장·공유가 핵심이다. 같은 4개 지표를 적용하면 셋 다 틀린다.

```
influencer_channels
  channel      text   -- blog | youtube | instagram | tiktok
  handle       text
  url          text
  analysis     text   -- 'active' | 'pending'   ← 지금은 blog 만 active
  verified_at  timestamptz
```

### ⑭ 블로그 등급 「베타」 표기

등급은 표본이 쌓일 때까지 계속 다듬는다. **그 사실을 먼저 밝힌다.**

- 「종합 등급」 카드 제목 옆에 앰버 `베타` 배지
- 점수 목록 아래 안내 박스 — 「데이터가 쌓이는 대로 배점과 구간을 다듬을 예정이라,
  활동이 그대로여도 등급이 조정될 수 있어요. 지금은 **참고 지표**로 봐주세요.」
- **광고주 검색 결과·프로필의 등급 옆에도 같은 베타 배지**를 단다.
  인플루언서에게만 알리고 광고주에게 안 알리면 신뢰 문제가 된다
- 등급을 숨기지는 않는다. 써봐야 어긋나는 지점이 드러난다

⚠️ 배점·구간을 조정할 때는 `blog_analytics_history` 에 **적용 버전(`score_version`)** 을 남긴다.
버전 없이 바꾸면 과거 등급과 비교가 안 되고, 왜 떨어졌는지 설명할 수 없다.

### ⑬ 「제목 그대로 검색」 제거

`keyword_rankings` 의 **제목 전체 검색은 지표에서 완전히 뺀다.**
자기 글 제목을 통째로 검색하면 거의 항상 1위라 변별력이 없다.

- 요약 스트립의 「제목 그대로 검색 7/7」 컬럼 삭제
- 행별 「검색 반영」 초록 배지 삭제 — 정상은 아무 표시도 하지 않는다
- **색인이 안 된 경우만** 빨강 「색인 안 됨」 배지. 이건 실제 문제 신호다
- 크롤러는 계속 수집하되(색인 확인용) 점수에는 반영하지 않는다

### ⑫ 키워드 체급 — 점수와 유형을 두 축으로

⑪의 유입량 점수만으로는 **난이도**가 안 보인다. 그렇다고 큰 키워드에 가산점을 몰면
지역 블로거가 다시 불리해진다. **한 점수로 합치지 말고 축을 나눈다.**

| 축 | 값 | 쓰임 |
| --- | --- | --- |
| 점수(등급) | 예상 유입량 | 얼마나 많은 사람을 데려오나 |
| 유형(체급) | 노출 키워드 검색량의 **중앙값** | 어떤 크기의 검색어에서 이기나 |

```
중앙 검색량 5,000+  → 대형 키워드형
        1,000–4,999 → 중형 키워드형
        ~999        → 롱테일형
```

- 유형은 **등급에 영향을 주지 않는다.** 우열이 아니라 용도다
- 화면 문구로 못박는다 — 「롱테일형은 낮은 등급이라는 뜻이 아닙니다.
  좁고 정확한 검색어에 강해 **지역 캠페인에 잘 맞습니다**」
- **광고주 검색 필터**에 유형을 넣는다. 이게 이 지표의 존재 이유다
  - 전국 브랜드 인지도 캠페인 → 대형 키워드형
  - 지역 매장 방문 유도 → 롱테일형
- 유형 칩은 **무채색 아웃라인**. 파랑은 공개 오픈 일정 전용이라 쓰지 않는다

**「메인 키워드 상위」 배지** — 월 검색량 1만 이상 키워드에서 10위 안을 하나라도 보유하면
등급과 별개로 배지를 단다. 큰 키워드 상위는 유입량과 별개로 난이도의 증거다.

### ⑩ 등급 구간 재조정 — 낮은 점수는 낮은 등급으로

```
S  90–100        (세부 없음 — 최상위 하나)
A  85–89 / 80–84 / 75–79     → A-1 / A-2 / A-3
B  70–74 / 65–69 / 60–64     → B-1 / B-2 / B-3
C  55–59 / 50–54 / 45–49     → C-1 / C-2 / C-3
D  40–44 / 35–39 / 0–34      → D-1 / D-2 / D-3
```
세부 번호는 **1이 위**. 총 13종.

- merry9849(35점) = **D-2**. 기존 B-3 표기는 잘못이었다
- 0점 항목을 빼거나 환산하지 않는다. **일 방문자 0점·이웃 0점도 그대로 반영**해 등급을 매긴다
- 등급 옆에 항상 「N점 · 다음 등급까지 M점」을 병기 — 무엇을 올려야 하는지 보이게
- 상위 등급 색은 초록, D 이하는 앰버/회색. 빨강은 쓰지 않는다(낙인)

⚠️ 낮은 등급의 맥락은 ⑨ 「이 블로그의 특징」이 담당한다. **등급을 후하게 주는 방식으로 보완하지 않는다.**

### 화면 반영
- 「내 채널」 화면 부제 문구 (프로토타입 반영됨):
  `blog.naver.com/xxx · **매일 밤 10시** 자동 수집 · 그날 올린 글까지 반영 · 광고주에게도 공개됩니다`
  ⚠️ 「어제 확정치」 같은 표현을 쓰지 않는다 — 22시 수집이라 **그날 글까지** 반영된다
- 「내 채널」 등급 배지 옆에 **결측 표시** — `측정 중 (일 방문자 수집 대기)`
- 등급 추이 스파크라인 (history 쌓인 뒤)
- 광고주 검색 카드의 등급 배지는 **결측 2개 이상이면 표시하지 않는다**
