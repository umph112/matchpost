# 0. 무엇을 만드나

인플루언서가 자기 오픈을 누르면 **그 오픈에서 시작된 협업이 하루 시간표로** 보이는 화면입니다.

「여수 1박 2일」처럼 며칠짜리 오픈 하나에 딜시트가 여러 개 붙습니다. 지금은 그것들이
따로 흩어져 있어서 **「그날 몇 시에 어디를 가고 총 얼마를 받나」를 볼 곳이 없습니다.**

# 1. 스키마

`sql/migrations/` 전체를 검색했습니다 — 둘 다 **없음**(0건).

```sql
-- sql/migrations/0090_proposal_stops_and_perk.sql

-- ① 한 건에 방문지 여러 곳
--    꼬북 두 지점을 묶어 10만원, 박람회장·돌산을 묶어 50만원처럼 여러 곳이 한 건인 경우가 흔하다.
--    방문마다 proposal 을 나누면 한 건이 두 건으로 세어지고 금액이 두 번 잡힌다.
create table if not exists proposal_stops (
  id          uuid primary key default gen_random_uuid(),
  proposal_id uuid not null references proposals(id) on delete cascade,
  at          time not null,          -- 방문 시각
  name        text not null,          -- 「여서점」 「돌산 진모지구」
  place       text,                   -- 간략 위치. 인플루언서가 적는다. 빈 값이 정상
  sort        int not null default 0
);
create index on proposal_stops (proposal_id, at);

-- ② 제공받는 것 (원고료와 별개)
alter table proposals add column if not exists perk text;
comment on column proposals.perk is
  '원고료 외에 제공받는 것. 「1박 제공」 「서비스 제공」. 인플루언서가 실제 받은 대로 고칠 수 있다.';

-- ③ 숙박 여부 — 시간 배정 규칙이 다르다
alter table proposals add column if not exists is_stay boolean not null default false;
```

⚠️ **`schedules.fee` 를 금액으로 쓰지 마세요.** `text`(「30만원~」)이고 오픈의 희망 페이입니다.
실제 금액은 `proposals.budget` 입니다.

# 3. 시간 배정 규칙

인플루언서가 시작·끝을 손으로 적지 않습니다. **협의된 시각에서 파생**됩니다.

| 종류 | 시간대 | 근거 |
| --- | --- | --- |
| 방문 (1곳) | 협의 시각 **−1시간 ~ +2시간** (앞1 + 본1 + 뒤1 = 3시간) | 준비와 이동이 늘 그만큼 든다 |
| 방문 (여러 곳) | **첫 방문 −1시간 ~ 마지막 방문 +2시간** | 방문마다 3시간을 따로 잡으면 16:00·17:00 연속 방문이 겹친다 |
| 숙박 | **20:00 → 익일 10:00** | 체크인·체크아웃 통상 시각 |

- 인플루언서가 고치면 그 값을 쓰고 **「직접 조정」**으로 표시합니다
- **숙박은 빈 시간 계산에서 뺍니다** — 자는 시간이라 다른 일정과 겹쳐도 됩니다.
  같이 계산하면 저녁 이후가 통째로 막혀 「하나 더 받을 수 있는 시간」이 사라집니다
- 시간표에서 숙박은 **맨 아래**에 둡니다. 하루를 덮는 일정이라 시각 순서에 끼우면 흐름이 끊깁니다

## 3-1. 숙박 협찬은 두 덩어리다

실제로는 **낮에 잠시 들러 촬영하고, 다른 일정을 소화한 뒤 저녁에 다시 가서 잡니다.**

- 촬영 블록 — 협의 시각 앞뒤 30분 + 본 30분 = **1시간 30분**. 낮 시간을 실제로 쓰므로 **빈 시간을 차지**
- 숙박 블록 — 20:00–10:00. 겹쳐도 됨
- 촬영 카드에는 **돈 줄을 반복하지 않습니다** — 「같은 건이에요 — 조건과 정산은 숙박 카드에 있어요」

한 건이 두 카드로 보이는데 금액이 두 번 나오면 두 건으로 읽힙니다.

# 4. 보수는 세 가지

**건마다 다릅니다.** 하나로 가정하면 나머지 둘이 깨집니다.

| 형태 | 화면 | 정산 |
| --- | --- | --- |
| 원고료만 | 금액 (검정 `#17171B`) | 받을 순서에 오름 |
| **제공만** | 「1박 제공」 (파랑 `#1D4ED8`) · 결제 줄은 **「결제 없음」** | 받을 순서에 안 오름 · 세무자료 「해당 없음」 |
| **원고료 + 제공** | 「300,000원 **+ 서비스 제공**」 | 금액만 정산 대상 |

⚠️ 제공만인 건에 **「0원」이라 쓰지 마세요.** 손해 본 건으로 읽힙니다.
⚠️ 제공만인 건에 **「결제일 미정」을 붙이지 마세요.** 정할 결제일이 남은 것으로 읽혀
인플루언서가 협의하러 갑니다.

## 4-1. 제공 표현은 인플루언서가 고친다

```
파란 점선 밑줄 (border-bottom:1px dashed #93C5FD · cursor:pointer)
```

광고주가 「서비스 제공」이라 적어도 실제로 무엇을 받았는지는 본인이 압니다 —
「저녁 2인 · 음료 포함」처럼 고쳐 적어두면 나중에 찾기 쉽습니다.

**금액은 못 고칩니다.** 합의된 값이고 대시에서만 바뀝니다. 점선을 긋지 마세요.

# 5. 간략 위치

**정확한 주소를 받지 않습니다.** 「오동도 근처」 정도만 적습니다.

| 결정 | 이유 |
| --- | --- |
| 주소 대신 간략 위치 | 주소를 다 입력하는 건 귀찮고, 안 적으면 화면이 빈다 |
| 이동 시간을 계산하지 않는다 | 직선거리 근사는 해안·산지에서 크게 틀린다. 틀린 안내는 없느니만 못하다 |
| 길찾기 링크도 두지 않는다 | 주소가 없으니 걸 곳이 없다 |
| 그래도 적게 하는 이유 — **다른 광고주가 대시했을 때의 판단 근거** | 「그 시간에 그 근처면 되겠다」가 보여야 빈 시간이 채워진다 |

⚠️ **빈 값이 정상 상태입니다.** 모르는 것을 추정해 채우지 마세요 — 본인 일정을 보면서
틀린 정보를 읽게 됩니다.
