# D6 결정 기록

각 규칙이 왜 그런지. 구현 중 판단이 필요하면 여기를 보세요.

---

## 대시 구조

| 결정 | 이유 |
| --- | --- |
| 광고주는 두 종류(캠페인 1:N / 개인 1:1), 인플루언서는 한 종류(전부 1:1) | 광고주는 여러 명을 동시에 다루고, 인플루언서는 광고주 한 곳만 상대한다. 인플루언서에게 방 종류를 알릴 이유가 없다 |
| 두 종류를 모양으로 구분한다 (파란 사각 / 노란 원) | 탭만으로는 스크롤하다 보면 어느 쪽인지 잊는다 |
| 방 헤더에 1:1 / 1:N 배지를 못박는다 | 목록에서 구분해도 방에 들어오면 다시 잊는다 |
| 광고주가 캠페인 대화에 쓴 말은 인플루언서의 1:1 창에 "단체 발송" 배지와 함께 도착한다 | 표시가 없으면 "나한테만 한 말"로 읽고 답장한다 |
| 인플루언서 대화 헤더는 "광고주와 나만 볼 수 있어요" | 여러 명이 있는 방인 줄 알면 할 말을 못 한다 |
| 캠페인 대화의 상대 말풍선에만 보낸 사람 이름을 붙인다 | 광고주에게는 여러 명이 섞여 들어온다. 1:1 에서 이름을 붙이면 시끄럽다 |
| 참여자를 고르면 그 사람에게만 간다 | 조건이 한 사람만 달라지는 일이 실제로 잦다 |
| 고르는 순간 확인 팝업을 띄운다 | 잘못 보내면 조건이 어긋나고 되돌릴 수 없다 |
| 고른 뒤에는 입력창 위에 계속 보이고 "전체로 되돌리기"가 옆에 있다 | 한 번 고르면 잊는다. 다음 메시지가 엉뚱하게 한 사람에게만 간다 |
| 개별 발송한 말은 "OOO님에게만" 배지로 남는다 | 나중에 조건이 갈린 원인을 찾을 수 있어야 한다 |

## 담당자

| 결정 | 이유 |
| --- | --- |
| 대화마다 담당자 한 명. 담당자가 아닌 직원은 관여 못 한다 | 업무 인계 없이 여러 사람이 끼어들면 인플루언서 쪽에서 누구 말이 맞는지 알 수 없다 |
| 예외는 소유자뿐이고, 그때는 "회사 대표 대리 발송" 표기가 남는다 | 드물지만 필요한 경우가 있다. 대신 누가 보냈는지는 반드시 남아야 한다 |
| 대화 헤더에 "담당 OOO" 배지 | 열자마자 내 대화인지 남의 대화인지 알아야 한다 |

## 대시의 정의와 알림

| 결정 | 이유 |
| --- | --- |
| 대시인지 아닌지의 기준은 "상대에게 처음 말을 거는가" 하나다 | 화면(오픈 · 검색 · 알림 · 친구)마다 다르게 세면 크레딧 계산이 갈린다 |
| 추천 알림에서 시작하는 말 걸기는 대시다 | 알림은 계기일 뿐이고, 실제로 말을 건 것은 사람이다 |
| 시스템이 만든 대화는 대시가 아니다 | 정산 지연 자동 알림 같은 것은 광고주가 건 말이 아니다 |
| 캠페인 맥락이 있는 알림은 새 대화를 만들지 않고 기존 대화로 들어간다 | 조건 · 일정 · 약속이 전부 거기 있다. 광고주 쪽에도 누가 말하는지 이름이 붙는다 |
| 자동 알림은 시스템 줄로만 남는다 (말풍선 아님) | 사람이 한 말과 섞이면 누가 한 말인지 흐려진다 |
| 캠페인 맥락이 없는 운영팀 알림은 알림함에만 쌓인다 | 답장할 상대가 광고주가 아니라 운영팀이다. 대화 목록에 섞이면 협업 대화가 묻힌다 |
| 운영팀과의 대화방은 만들지 않는다 | 대화방을 열면 운영팀이 실시간 응대를 떠안는다. 감당할 수 있는 형태로 설계한다 |

## 날짜 제안

| 결정 | 이유 |
| --- | --- |
| 대시를 보낼 때 날짜를 고른다. 글로 쓰지 않는다 | 대화에 글로만 적으면 딜시트 · 달력 · 정산이 읽을 수 없다 |
| 오픈을 보고 보내면 그 오픈일이 기본 선택지 | 오픈일과 다른 날을 제안하는 일이 흔하다 |
| 오픈이 없는 상대에게도 날짜 질문은 나온다 | 날짜 없이 시작하면 딜시트가 만들어질 근거가 없다 |
| 날짜가 비면 보낼 수 없다 | 날짜를 물어놓고 답 없이 보내면 예전 상태로 되돌아간다 |
| 제안은 말풍선이 아니라 카드로 남는다 | 수락 여부가 딜시트로 이어지므로 눈에 띄어야 한다 |
| 내가 보낸 제안에는 수락 버튼이 없다 | 자기 제안을 자기가 확정하면 협의가 아니다 |
| 날짜 변경은 양쪽 수락을 초기화하지 않는다 | 제안 -> 수락이 이미 합의다. 거기서 "다시 눌러주세요"는 같은 합의를 두 번 시키는 것이다 |
| 합의된 날짜는 곧바로 진행일이 된다 | "협의중"으로 남기면 날짜를 정하고도 수락할 수 없는 막다른 길이 생긴다 |
| 페이 · 미션 등 날짜 아닌 조건은 대화에서 따로 합의한다 | 날짜 변경 창이 다른 조건까지 바꾸는 통로가 되면 무엇이 합의됐는지 흐려진다 |

## 취소

| 결정 | 이유 |
| --- | --- |
| 취소 수락은 딜시트까지 간다 | 대화는 취소인데 딜시트는 진행중이면 어느 쪽이 참인지 알 수 없다 |
| 취소된 사람은 모든 파생 숫자에서 빠진다 | 파생값이 취소를 모르면 예산이 부풀려 보이고, 취소된 사람의 세무자료를 계속 요구하게 된다 |
| 취소된 행은 지우지 않고 남긴다 | 무슨 일이 있었는지가 곧 기록이다 |

## 캠페인 일정

| 결정 | 이유 |
| --- | --- |
| 일정의 원본은 등록 때 광고주가 정한 기본 일정이다 | 지역 · 제품 · 기자단 모두 광고주가 기본을 정해놓고 시작하는 것이 실무다 |
| 방문일에서 기한을 자동 파생하지 않는다 | 방문일이 달라도 게재를 같은 날로 묶고 싶은 광고주가 있다. 자동 파생은 그 선택을 빼앗는다 |
| 그 사람만 달라진 경우에만 개별 값이 기본을 덮고 "(변경)"으로 표시된다 | 기본과 다르다는 사실이 보여야 왜 다른지 물어볼 수 있다 |
| 진행 과정은 조립식이다 | 방문은 지역에만, 수정 방식은 캠페인마다 다르다 |
| 수정 방식은 두 갈래 - 사전 컨펌과 게재뒤수정 | 원고를 미리 받는 곳도, 일단 올리고 고치는 곳도 실제로 많다 |
| 사전 컨펌을 끄면 게재뒤수정이 자동으로 켜진다 | 가장 흔한 대안이라 먼저 제안한다. 필요 없으면 한 번 더 눌러 끈다 |
| 둘 다 끌 수 있다 | 가이드대로 올리면 끝내는 광고주도 있다 |
| 원고 단계는 사전 컨펌에 딸린다 | 원고 칩만 켜져 있고 원고 마감이 없으면 딜시트에 갈 곳 없는 단계가 남는다 |
| 뺀 단계에 있던 사람은 다음 살아 있는 단계로 읽는다 | 없는 단계 이름이 표에 남으면 안 된다 |
| 확정 인원이 생기면 단계 구성을 못 바꾼다 | 진행 중에 단계가 사라지면 이미 완료한 체크가 허공에 뜬다 |
| 인플루언서는 자기 일정에 맞는 딜시트를 본다 | 남의 일정이 섞이면 자기 마감을 못 찾는다 |

## 정산

| 결정 | 이유 |
| --- | --- |
| 세 콘솔의 "오늘"은 하나다 | 광고주만 다른 날짜를 써서 같은 미수 건이 D+8 과 D+13 으로 갈렸다 |
| 광고주 정산에 미수 상태를 둔다 | 예정일이 지난 건이 인플루언서 · 관리자 화면에만 뜨고 광고주 화면엔 없었다. 그러면 "나는 몰랐다"가 성립한다 |
| 미수 카드는 어디에 어떻게 보이는지를 광고주에게 알린다 | 결과를 알아야 움직인다 |
| KPI 두 번째 칸은 "가장 가까운 정산일"이 아니라 미수 | 급한 것이 위에 있어야 한다 |
| "정산 완료로 기록"은 카드를 실제로 완료로 옮긴다 | 모달만 닫히면 기록됐는지 알 수 없다 |
| 세무자료 "요청 보냄"은 캠페인마다 따로 남는다 | 하나로 두면 한 곳에서 보내고 다른 캠페인도 보낸 것처럼 보인다 |
| 진행바 분모는 정산 대상 인원 (보류자 제외) | 보류자를 넣으면 영원히 100% 가 안 된다 |
| 관리자 광고주별 미수는 미수 목록에서 파생 | 따로 적어서 "목록에 없는 광고주가 미수 2건"이 되어 있었다 |
| 지연 0건이면 "평균 N일 지연"을 쓰지 않는다 | 두 값이 어긋나면 표 전체를 못 믿는다 |
| 지연 알림은 매일 1회 자동 발송, 누적이 제재 근거 | 인플루언서가 혼자 재촉하지 않아도 되고, 횟수가 곧 근거다 |
| 협의로 예정일을 바꾸면 지연이 아니다 | 알림이 멈추고, 빠져나갈 길을 함께 알려준다 |

## 신고

| 결정 | 이유 |
| --- | --- |
| 신고 입구는 대화 헤더 한 곳뿐 | 입구가 여러 곳이면 어디서 냈는지에 따라 유형이 갈린다 |
| 유형 목록은 관리자 REPORT_TYPES 에서 역할별로 잘라 쓴다 | 목록이 갈리면 관리자의 유형별 집계가 어긋난다 |
| 유형 + 설명 둘 다 필수 | 운영팀이 읽고 판단할 근거가 그것뿐이다 |
| 신고하면 대화에 남고 버튼이 "신고 접수됨"으로 바뀐다 | 냈는지 안 냈는지 화면이 말해줘야 같은 건을 또 내지 않는다 |
| 모달 첫 줄은 "매치포스트는 판정하지 않습니다" | 중재자로 오해하면 기대가 어긋나고 분쟁이 커진다 |
| 접수 = 대화 / 결과 = 알림함 / 추가 문의 = 고객센터 | 결과가 대화로 오면 운영팀에 답장하려 들고, 그 답이 상대에게도 보인다 |
| 피신고자는 신고를 닫을 수 없다 | 닫는 권한은 신고자와 운영자에게만 있다 |

## 크레딧

| 결정 | 이유 |
| --- | --- |
| 값의 원본은 카탈로그 하나 | 같은 항목이 화면마다 3,000 / 1,000 / 500 으로 갈려 있었다 |
| 지급과 차감은 charge() 하나를 지난다 | 함수 밖에서 잔액을 건드리면 원장과 잔액이 어긋난다 |
| 베타 무료는 값을 0 으로 만드는 것이 아니라 청구만 끄는 것이다 | 원래 값을 함께 보여주면 유저가 미리 가격을 익힌다. 나중에 스위치만 켜면 된다 |
| 정책 변경은 30일 전 공지 + 유예 후 시행, 소급 없음 | 진행 중인 협업의 크레딧을 소급하면 신뢰가 깨진다 |
| 지급 액션에는 상한을 둔다 | 없으면 오픈을 반복 등록해 크레딧을 찍어낸다 |
| 크레딧은 취소해도 회수하지 않는다 | 회수하면 취소를 숨기려 든다 |
| **유료화는 구독과 이용권만. 금액 충전 UI 를 만들지 않는다** | "10,000원 = 10,000C" 는 선불전자지급수단에 해당해 전자금융업 등록 대상이 될 수 있다. 자본금 요건이 커서 초기에는 불가능하다 |

## 법무

| 결정 | 이유 |
| --- | --- |
| 사업자 정보는 인트로(초기 화면) 하단에 표시한다 | 전자상거래법 제10조가 요구하는 곳이 초기 화면이다 |
| 개인정보처리방침 링크는 굵게 | 법령이 소비자가 쉽게 찾을 수 있도록 요구한다 |
| "사업자정보 확인"을 따로 둔다 | 표시한 정보의 진위를 확인할 수 있어야 한다 (시행규칙 제7조 2항) |
| 통신판매중개자 면책 문구를 함께 둔다 | 매치포스트는 거래 당사자가 아니다. 이 문장이 없으면 중개자가 판매자로 오인된다 |
| 콘솔에는 사업자 정보를 넣지 않고 약관 링크만 둔다 | 법이 요구하는 곳은 초기 화면이다. 앱처럼 쓰는 화면에 법정 고지를 반복하면 밀도만 해친다 |
| 대시 첨부파일은 7일 뒤 자동 삭제 | 우리가 갖고 있을 이유가 없다. 보관 자체를 줄이는 것이 가장 안전한 보호다 |
| 삭제 후에도 파일명 · 시각 · 보낸 사람은 남긴다 | 분쟁에서 확인할 것은 내용이 아니라 "언제 무엇을 보냈는가"다 |
| 자격 확인 서류는 확인 즉시 삭제, 결과와 등록번호만 보관 | 국외 이전에서 가장 무거운 항목을 빼는 방법이다 |
| Supabase 는 서울 리전을 쓴다 | 데이터가 국내에 머물러 국외 이전 고지 부담이 줄고 속도도 붙는다 |
| 서울 리전을 써도 국외 이전으로 보아 고지한다 | 운영 · 장애 대응 과정에서 해외 사업자가 접근할 수 있다. 실제 상황을 그대로 쓰는 편이 나중에 문제가 없다 |
