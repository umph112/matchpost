# 1. `proposals` 를 원본으로 다시 만든다

## 1-1. 매출의 정의

| 상태 | 조건 | 화면 라벨 |
| --- | --- | --- |
| 예정 | 양쪽 확정 · `settlement_status !== '완료'` · 예정일 안 지남 | **예정** |
| 미수 | 양쪽 확정 · `settlement_status !== '완료'` · **예정일 지남** | **미수** |
| 수금 확인 | `settled_at` 있음 · `paid_confirmed_at` 없음 | **확인 대기** |
| 완료 | `paid_confirmed_at` 있음 | **완료** |

⚠️ 지금 `STATUS_FILTERS = ['전체','예정','진행중','완료','결제완료']` 는
`earnings.status` 문자열이라 위 상태와 무관합니다. **위 네 개로 바꾸세요** —
`['전체','예정','미수','확인 대기','완료']`.

「진행중」과 「완료」·「결제완료」가 무엇이 다른지 화면에서 구분되지 않았습니다(D7 §5-3 지적).
위 정의로 바꾸면 그 문제가 함께 해소됩니다.

## 1-2. 쿼리

```
proposals
  where influencer_id = 나
    and advertiser_confirmed = true
    and influencer_confirmed = true
  join campaigns (title, brand_name, settlement_date, overdue_reminder_count)
  join advertiser_profiles (company_name)
  join profiles (name)          -- 담당자
```

- **금액은 `proposals.budget`** 입니다
- **귀속 기준은 결제 예정일 하나** (`campaigns.settlement_date`) — 모든 상태 공통. (PROMPT-2 정정)
  실제 입금일(`paid_confirmed_at`)로 옮기지 않습니다. 8월 건을 10월에 받아도 8월 매출입니다.
  입금이 확인돼도 원래 예정일의 매출로 확정됩니다
- 미수 판정은 이미 있는 로직(`earnings/page.tsx` 의 overdue 블록)을 그대로 재사용하세요.
  같은 기준이어야 세 화면(인플루언서·광고주·관리자)의 미수가 일치합니다

## 1-3. 요약 카드 — 네 칸

```
예정 매출    예정 상태의 합
미수         미수 상태의 합 · 0원이 아니면 빨강
확인 대기    settled_at 있고 미확인인 것의 합
```

**스코프 (PROMPT-3 확정):**

# 2-5. 직접 등록한 일 — 확인 후 결정

인플루언서는 **매치포스트 밖의 일정도 자기 달력에 기재**합니다 (「내 일정」 화면 ·
점선 = 직접 등록, 실선 = 시스템 생성). **전체 일정 관리를 매치포스트에서 하게 하려는 것**이고,
거기에는 두 종류가 섞여 있습니다:

| 종류 | 예 | 매출인가 |
| --- | --- | --- |
| 밖에서 생긴 **돈 버는 일** | 다른 경로로 받은 협찬 · 외주 촬영 | **매출** |
| 그냥 개인 일정 | 병원 · 여행 · 가족 행사 | 아니다 |

**금액이 적힌 것만 매출에 합산합니다.** 개인 일정은 달력에만 있고 매출 화면에 나오지 않습니다.
그래서 직접 등록 폼의 **금액은 선택 필드**여야 합니다 — 필수로 두면 개인 일정을 못 적습니다.

⚠️ **등록을 쉽게 만드는 것이 이 기능의 핵심입니다.** 매치포스트를 중심으로 자기 일정을
보게 하려는 것이고, 협업 건만 있는 달력은 하루에 한 번도 안 열게 됩니다.
**날짜 · 제목만으로 저장되게** 하고 나머지는 다 선택으로 두세요.

`earnings` 가 원래 이 자리였을 가능성이 있습니다(그런데 insert 경로가 없어 결국 안 쓰였습니다).

**먼저 확인해 주세요 — 직접 등록 건이 어디에 저장되고, 금액 필드가 있나요?**

```bash
grep -rn "직접 등록\|is_manual\|source.*manual" src sql | grep -v transfers
grep -n "amount\|budget\|fee" sql/migrations/*schedule*
```

| 확인 결과 | 그러면 |
| --- | --- |
| 금액 필드가 **있다** | **금액이 적힌 건만** 매출 화면에 합산. 「직접 등록」 배지로 구분하고 요약에 「매치포스트 N원 · 직접 등록 N원」을 나란히 |
| 금액 필드가 **없다** | 이번 회차는 `proposals` 만. 직접 등록에 **선택 금액 필드**를 추가하는 것은 별도 건 |

⚠️ **금액은 선택 필드**입니다. 필수로 두면 병원·여행 같은 개인 일정을 못 적습니다.
달력의 목적은 전체 일정 관리이고, 매출은 그중 금액이 적힌 것만입니다.

⚠️ **합산하더라도 원본은 두 개로 유지합니다.** 하나로 합치는 테이블을 새로 만들지 마세요 —
매치포스트 건은 우리가 아는 사실이고 직접 등록은 본인이 적은 것이라, 성격이 다릅니다.
화면에서 나란히 보여주고 배지로 구분하는 것으로 충분합니다.

⚠️ **미수는 매치포스트 건에만** 씁니다. 직접 등록 건의 미수는 우리가 알 수 없습니다.
