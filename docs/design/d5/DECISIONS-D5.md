## D5 구현 중 결정 (2026-08-05, 레포 구조 확인 후)

레포에 스펙이 전제한 구조가 없어서 그 자리에서 정한 것들이다.

| 결정 | 이유 |
| --- | --- |
| 대시 탭(캠페인 대화 / 개인 대화) UI는 이번에 만들지 않는다. 대신 필터 수를 "지금 렌더되는 목록 배열"에서 세게 한다 | 탭은 1:N 캠페인 대화방이 있어야 의미가 있고 그 구조가 아직 없다. 세는 기준만 먼저 맞춰 두면 탭이 생겨도 코드를 안 고친다 |
| 대시 발송은 서버 액션 sendDash 하나로 통일 (proposals 행 생성 + 대화 생성/조회 + 시스템 메시지 + 알림, 크레딧 0) | 긴 폼(/proposals/new)은 행만 만들고 대화를 안 열었고, 캘린더 발송은 대화만 열고 행을 안 만들었다. 두 갈래가 서로 다른 상태를 남긴다 |
| 발송 후 이동 경로는 /advertiser/messages?c=<대화 id> 한 가지 | 어디서 보냈든 결과가 같은 자리에 보여야 "보냈다"가 확인된다 |
| 검색 · 내 인플루언서 · 프로필 오픈 행에 발송 버튼을 신설. 긴 폼은 "조건까지 채워 보내는" 경로로 남긴다 | 사람을 찾은 자리에서 바로 보내야 한다. 긴 폼을 유일한 입구로 두면 대시가 무거워진다 |
| 재전송은 새 proposals 행을 만들지 않고 기존 "응답 대기" 행을 수정 + 시스템 메시지 1줄 + 알림 재발송 | 행이 쌓이면 무엇이 유효한 제안인지 알 수 없다. 이력은 대화가 갖는다 |
| 기존에 proposals 행 없이 만들어진 대화는 백필하지 않는다 | 과거 데이터를 손대면 검증이 불가능해진다. 신규 발송부터 규칙을 지키면 충분하다 |
